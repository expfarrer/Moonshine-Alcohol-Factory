	/* ------------------------------------------------------------------
	   Flavored White Lightning (v1: WhiteLightning jar only).
	   Same booze (AlcoholPower/ThirstChange held at the WhiteLightning
	   baseline), softened StressChange/UnhappyChange -99 -> -85: that IS
	   the flavor mechanic.  Deliberately NON-perishable like the parent
	   (Packaged = TRUE, no DaysFresh/DaysTotallyRotten) even though the
	   fruit input is perishable.

	   SPOILAGE INHERITANCE -- verified headlessly 2026-09-05
	   (tools/pzrepl/tests/flavor.lua): a craft output does NOT inherit its
	   inputs' age or rot.  Both behaviours are opt-in per-input flags that
	   these recipes deliberately do not set:
	     flags[InheritFoodAge]   -- would copy the fruit's age onto the jar
	     flags[AllowRottenItem]  -- would let a rotten fruit be used at all
	   Measured: fresh apple and a 7.5-day apple both yield age=0,
	   OffAge/OffAgeMax = 1000000000 (the "never spoils" sentinel, straight
	   off this script, identical to the parent WhiteLightning), and
	   setAge(100000) on the result still reads isRotten() == false.
	   A fully rotten fruit simply makes the recipe UNAVAILABLE.
	   ------------------------------------------------------------------ */

	/* ------------------------------------------------------------------
	   BACKLOG 1.4 -- WHISKEY BY AGING, a 3-STAGE LADDER.

	     craftRecipe CharAndAgeWhiteLightning
	       Moonshine.WhiteLightning + 2 charcoal
	         -> WhiteLightningCharred  "Charred Oak Shine (1/3)"
	         -> (30 days, unattended)  WhiskeyGreen "Green Whiskey (2/3)"
	         -> (90 days total)        WhiskeyScarletOak "Scarlet Oak Whiskey"

	   Only the FIRST step is a craft.  The other two are `ReplaceOnRotten`
	   swaps driven by the item's own age -- quirks rule 69, which proves the
	   engine is completely indifferent to the DIRECTION of the swap (vanilla's
	   own SugarBeetSyrupPot -> SugarBeetSugarPot is the same positive shape).
	   `Moonshine.WhiteLightning` itself is deliberately UNCHANGED and stays
	   non-perishable; nothing here alters the flagship jar.

	   THREE HARD CONSTRAINTS, all measured live 2026-09-06
	   (tools/pzrepl/probes/probe_aging_ladder.lua, 63 assertions, 0 failures):

	   (a) EVERY `ReplaceOnRotten` TARGET MUST BE `ItemType = base:food`.
	       Anything else makes InventoryItemFactory.CreateItem() return null and
	       the SOURCE IS DESTROYED WITH NOTHING CREATED -- a silent vanish with
	       only a server-log WARN.  Verified here as a deliberate control.  All
	       three items below are base:food; verify any future link the same way.

	   (b) THE TARGET INHERITS THE SOURCE'S `age`, so each stage needs a
	       strictly LARGER `DaysTotallyRotten` than the age it inherits, or the
	       whole ladder would cascade in a single tick.  30 -> 90 -> none.
	       Measured: stage 2 inherits age 30.5 against its own 90, not rotten.

	   (c) THE TARGET'S NUTRITION IS OVERWRITTEN BY THE SOURCE'S:
	       HungerChange, UnhappyChange, BoredomChange, Calories, Carbohydrates,
	       Lipids, Proteins all arrive from the previous stage.  So all three
	       declare IDENTICAL nutrition (the WhiteLightning baseline) and the
	       ladder is differentiated ONLY through StressChange, AlcoholPower and
	       DisplayName -- fields the target demonstrably KEEPS.  Measured: a
	       source with Calories forced to 9999 produced a stage 2 reading 9999
	       calories but stage 2's own StressChange -0.75 and AlcoholPower 1.25.
	       NEVER try to make an aged stage "better" via Calories/UnhappyChange.

	   NO `DaysFresh` ON ANY STAGE.  That keeps offAge at the 1e9 sentinel,
	   which suppresses the "(Fresh)" / "(Stale)" name prefix completely (and
	   with it every stale hunger/thirst/texture penalty).  Measured: the
	   stage-1 name is identical at ages 0 / 1 / 10 / 20 / 29.99.  The price is
	   that B42 has no freshness bar at all, which is exactly why this is a
	   3-stage ladder: the DisplayName is the ONLY progress feedback a player
	   ever gets, so the stage number lives in the name.

	   TUNING.  Aging is `age += (worldAgeHours - lastAged) * FoodRotSpeed / 24`,
	   a catch-up model, so it also runs in unloaded chunks and survives
	   save/reload.  The sandbox Food Rot Speed option scales it 0.4x-1.7x, so
	   the nominal 30 / 90 days is really 18-75 / 53-225 days, and a POWERED
	   FRIDGE applies a further 0.2x.  Both are documented in the tooltips.

	   KNOWN, ACCEPTED: a jar drunk down to half and THEN aged carries its
	   half-empty HungerChange across the swap (inherited, per (c)) but its
	   ThirstChange resets to the new stage's script value (kept, per (c)).  So
	   part-drinking an aging jar hands back the thirst half of one jar after 30
	   in-game days.  That is engine behaviour common to every ReplaceOnRotten
	   chain including vanilla's, the reward is far smaller than the wait, and a
	   workaround would cost more than it saves.
	   ------------------------------------------------------------------ */

	   Originally shipped in acef84b and reverted in 3b7121c because the recipe
	   never consumed the bucket; quirks rule 65 explains that (a real
	   `component FluidContainer` input needs flags[ItemCount]) and the recipes
	   below now carry the flag.

	   NUTRITIONALLY THIS IS WhiskeyRefill, byte for byte (HungerChange -10,
	   Calories 1200, AlcoholPower 2, UseDelta 0.25 -> 4 sips).  That is
	   deliberate: no balance number is being invented here.  A bucket of
	   spirit is worth exactly one whiskey bottle and weighs 4.0 instead of
	   0.7, i.e. it is a strictly heavier container for the same drink, so
	   adding it cannot inflate the spirit economy.

	   Two fields differ from the 2026-08-26 original, both measured:
	     ReplaceOnUse      Base.BucketEmpty, not the bare `BucketEmpty`
	                       (rule 66: a bare token in this field is
	                       MODULE-scoped).  WhiteLightning already does this.
	     WorldStaticModel  Bucket_Ground_Fluid, not BucketFullWater_Ground --
	                       the latter resolves to nothing ("???." in
	                       ModelScript.check, see the sibling BucketWaterRefill
	                       which still has the dead reference). */

	    StressChange	=	-50,
	    DisplayCategory = Food,

		/* Weight 2.0 = container + contents (quirks rule 68), not an arbitrary
		   "heavier than a bottle" anti-exploit number. RefillSpiritInBucket3/4/5

		   still pot (bare `item 1 [pot]`, rule 37) regardless of tier -- NOT the

		   11 = 1.0 container + 10 L water, i.e. 1.0 weight/L): 1.0 (bucket,

		   1 L serving) = 2.0. Previous value (4.0) was carried over unchanged
